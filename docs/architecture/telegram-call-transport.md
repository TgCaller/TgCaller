# Telegram group-call transport: implementation boundary

## Current status

TgCaller has a transport delegation boundary in `tgcaller.mtproto.Connection`, but it does **not** yet include a production Telegram group-call transport. Without an explicitly injected backend, join and media operations fail rather than report simulated success.

The test-only `FakeTransport` in `tests/test_client.py` validates client orchestration only. It does not prove that a Telegram call can be joined or that media reaches Telegram.

## Why signaling alone is insufficient

Telegram's official group-call API requires `phone.joinGroupCall` to receive a `params` payload generated by a local group-call media engine. The payload includes a non-zero audio SSRC, ICE username fragment/password, DTLS fingerprints, and video SSRC groups when publishing video. The response includes connection parameters that the local media engine must consume.

Reference: https://core.telegram.org/method/phone.joinGroupCall

The call lifecycle also needs to handle `phone.checkGroupCall` source checks, call updates, leaving the call, reconnecting ICE/DTLS/media sessions, and any server-selected stream-mode response. A generic WebRTC peer connection is not automatically a Telegram-compatible implementation merely because it supports ICE and DTLS.

Reference: https://core.telegram.org/api/group-calls

## Active-call resolution helper

The signaling adapter now exports `resolve_active_group_call(client, chat_id)`.
It uses Pyrogram's raw full-chat methods to retrieve the active `InputGroupCall`
for a basic group, supergroup, or channel. It fails with an actionable
`ConnectionError` if the chat cannot be resolved or has no active call.

```python
from tgcaller.mtproto import PyrogramGroupCallBackend, resolve_active_group_call

backend = PyrogramGroupCallBackend(
    client=app,
    resolve_call=lambda chat_id: resolve_active_group_call(app, chat_id),
    media_engine=your_telegram_compatible_media_engine,
)
```

This helper only resolves the signaling target. It does not create a call,
generate join parameters, or implement audio/video transport. A real
`TelegramMediaEngine` implementation is still required.

## Required implementation stages

1. **MTProto signaling adapter** — resolve the active `InputGroupCall`, invoke the official raw API methods, parse returned updates, and track call IDs/access hashes and SSRCs.
2. **Independent media engine** — generate Telegram-compatible join payloads, negotiate ICE/DTLS, encode/decode audio/video, and exchange packets using Telegram's expected transport behavior. Do not report a join as successful until this engine reaches a connected state.
3. **Lifecycle and recovery** — leave cleanly, check registered sources, handle server updates, rejoin on missing sources, and cancel all background tasks.
4. **Media pipeline** — connect file/URL decoding and frame production to the real media engine; implement pause/resume/volume only where the transport can actually apply them.
5. **Integration verification** — test with a real Telegram test group call and at least two accounts, verifying join/leave, audible playback, participant updates, reconnect, and cleanup. Unit tests and a successful wheel build are necessary but not sufficient.

## Acceptance criteria

- No simulated success in production code.
- `join_call` succeeds only after Telegram signaling and the local media engine have both succeeded.
- Missing or unsupported transport features raise an actionable error.
- Unit tests use explicit fakes; live integration tests are separately marked and run only with configured test credentials.
- No runtime dependency on PyTgCalls. Any reused protocol knowledge must be implemented and tested in TgCaller's own adapter/engine.

## TgCaller-owned media engine plan

The implementation decision and staged acceptance gates are documented in [Telegram media engine implementation contract](telegram-media-engine.md). TgCaller will not adopt PyTgCalls or NTgCalls as its runtime media engine. Lower-level libraries may be used as building blocks, but Telegram-specific negotiation, lifecycle, recovery, and the public API remain TgCaller-owned. The engine is not complete until a live Telegram call proves actual media flow.
